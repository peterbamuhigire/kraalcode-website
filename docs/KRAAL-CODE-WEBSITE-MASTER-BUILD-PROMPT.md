## 2. Product and brand thesis

Use the following thesis as the starting position, then refine its wording against the SDLC documentation and verified evidence:

> Kraal Code is the operating system for the modern African organisation: one secure cloud platform for running finance, people, stock, sales, procurement, production, projects, field operations, and management from wherever work happens.

This thesis has four connected narrative pillars.

### 2.1 Run the whole organisation

Show how connected modules replace fragmented spreadsheets, disconnected apps, manual handoffs, delayed reports, duplicated data, and management blind spots.

Do not sell “features” in isolation. Translate each verified capability into an organisational outcome, such as:

- one source of operational truth;
- controlled approvals and accountability;
- real-time visibility across locations;
- faster, cleaner financial operations;
- traceable inventory and procurement;
- coordinated people and project work;
- stronger management decisions;
- less dependency on one physical office or one key employee.

### 2.2 Built for African operating realities

Present African-market fit as practical competence, not as visual decoration or vague pride language. Where supported by evidence, communicate matters such as:

- multi-branch and distributed operations;
- field and mobile work;
- intermittent or expensive connectivity considerations;
- regional language needs;
- local currencies, tax, payroll, statutory, and reporting realities;
- organisations that combine formal offices with warehouses, agents, projects, farms, factories, shops, or field teams;
- usability for teams that should not require weeks of ERP training;
- a support and implementation model grounded in the region.

Never imply that Africa is a single homogeneous market. Distinguish country-specific facts, legal requirements, terminology, currency, and language decisions.

### 2.3 Work from anywhere

Make “your organisation travels with you” a central story. Show Kraal Code as the controlled digital environment through which authorised people can work from:

- a laptop at headquarters;
- a phone in the field;
- a tablet in a warehouse or shop;
- a remote home office;
- another branch, city, or country;
- a management meeting requiring live operational visibility.

Avoid suggesting that every workflow has identical functionality on every device unless the product evidence proves this. Distinguish responsive web access, mobile-specific capabilities, offline capabilities, and roadmap items.

### 2.4 Security, privacy, and control as product value

Security must be visible throughout the buyer journey, not confined to a footer badge. Present security and privacy as business-enabling controls: they make remote work, delegation, branch operations, cloud access, and global collaboration possible without abandoning accountability.

Potential themes include tenant isolation, role-based access, permission controls, audit trails, secure sessions, encryption, MFA, backups, retention, monitoring, change control, secure software development, incident response, and data rights. However, publish only controls verified by current product documentation or implementation evidence.

Never use unsupported phrases such as “bank-grade security”, “military-grade encryption”, “100% secure”, “fully compliant with all laws”, “GDPR certified”, “ISO certified”, “SOC 2 compliant”, “zero downtime”, or “unhackable”.

## 3. Non-negotiable truth and claim policy

Treat every public statement about capabilities, customers, results, security, privacy, law, standards, certifications, availability, data location, support, pricing, integrations, and roadmap status as a claim requiring ownership and evidence.

Create a claim register before drafting public copy. Use at least these fields:

| Field | Required meaning |
| --- | --- |
| Claim ID | Stable identifier |
| Draft claim | Proposed public wording |
| Claim category | Product, security, privacy, legal, performance, customer, commercial, market, or roadmap |
| Source | Exact document, URL, implementation evidence, or named owner |
| Source location | Heading, page, line, control ID, or other locator |
| Status | Verified, qualified, planned, aspirational, disputed, expired, or not assessed |
| Scope | Product edition, module, geography, customer type, environment, and date |
| Public wording | Final bounded wording allowed on the site |
| Review owner | Product, security, legal, finance, marketing, or executive owner |
| Review/expiry date | When the claim must be rechecked |

Rules:

1. Only **verified** or deliberately **qualified** claims may appear as current public facts.
2. Planned capabilities must be explicitly labelled as roadmap/future items and should normally remain off money pages.
3. Aspirational claims stay in internal strategy documents.
4. Certifications may be displayed only when the certificate, scope, validity period, and permission to publish are available.
5. A legal compliance claim requires current primary legal sources and qualified legal review. Technical teams may document controls and alignment; they may not self-certify legal compliance.
6. Customer logos, testimonials, usage numbers, outcomes, awards, and partner marks require attribution and permission.
7. Do not convert a design intention into a product fact.
8. If evidence is missing, create a visible gap in the internal register and use narrower copy; never fill the gap with plausible language.

Every research subtask must inherit this exact clause:

```text
HARD CONSTRAINT — NO HALLUCINATION:
- Do NOT invent statistics, names, organisations, court cases, statutes, or URLs.
- Cite every numeric claim and every direct quote at the point it appears.
- If you cannot find a source for a fact, mark it as a "gap" — do not fabricate filler.
- For any claim you assemble from multiple sources, mark it "(synthesis)".
- For any inference, mark it "(inference)".
- Verbatim quotes must reproduce text exactly as it appeared in the source — no creative editing.
- If a search returns nothing, report "no source found" — do not write what is plausible.
```
